# MealForward 新产品全栈 MVP 验收与交接（2026-10-31）

## 交付边界

本轮将此前的独立业务模块接成真实 PostgreSQL、链上合约、平台 Claim 签名、HTTP/SIWE 和浏览器界面。新增入口 `/product-v2/index.html`；旧公网 `/mvp/product.html` 不代表此版本。本轮没有迁移旧库、替换旧合约或操作用户的钱包，两笔旧 SETTLED 记录保持原状。

当前有两个严格隔离的运行配置：

- `local-acceptance`：本机 127.0.0.1、独立 PostgreSQL 17、Anvil 31337、本次随机测试账户和 TEST 代币。使用明确标记的本地测试钱包，包含真实签名、交易、收据和数据库写入，不是 mock API。
- `monad-testnet`：默认生产入口要求 HTTPS、新专用数据库角色、新合约 manifest、独立 Claim/验券权限及固定 10143 测试资产。启动验证失败即关闭业务。入口代码具备不等于已完成公网部署；本轮的本地测试不冒充 MetaMask 或 Monad 公网验收。

原 Site v8 `e412ae14` 的流程依据与三版本区别，见 [原流程文档](2026-10-30-product-flow-and-integration.md)。此前核心模块阶段的 250 项测试记录见 [上一阶段](2026-10-30-product-foundation-implementation.md)，不能与本轮不同测试口径简单相加。

## 已接通的用户流程

1. 商家钱包登录 → 登记厨房 → 新增餐品 → 校验及审核 → 钱包确认发布。支持新版本、补量、资助期限、上下架、公告和今日休息。
2. 支持者浏览厨房 → 选份数 → 审核金额 → 精确代币授权 → 明确确认资助 → 查询原交易和支持历史。资助成功不会自动领取。
3. 领取者登录 → 选已资助餐品 → 审核并领取 → 平台承担链上手续费 → 私有餐券及保存链接。打开链接必须重新验证原领取钱包。
4. 餐券在原承诺时段内显示短时凭证 → 商家检查 → 唯一处理权 → 勾选实际已交餐 → 商家钱包确认 → 等待 180 秒 → 审核结算并收款。
5. 公共账显示经过链上核验的汇总及已核验的应用内支持记录；不返回领取秘密或领取钱包。公开记录列表最多 200 条，不宣称覆盖所有外部链上交易。
6. 切钱包、刷新、关闭弹窗、断网时保留原操作。后台只查询已知交易；缺失返回哈希可从原钱包记录补入，不能靠再次付款恢复。资助索引匹配原 requestId 和付款钱包后，也必须经过完整原交易核验才能恢复。

页面保留厨房、资助、我的支持、我的餐券、商家工作台及公共账的边界；编辑、审核及处理进度使用弹窗。未纳入本次 MVP 的内容包括真实 NFT 铸造、餐品图片上传及原 Site 全部附属展示页面，不能称为完整视觉复刻。

## 本轮新增的永久停业规则

用户已明确：**未交餐的有效券立即失效，餐款退回资助者，同时解除对应领取人的领取间隔。** 无需再次确认。

- 商家明确确认 `closeStore` 后，尚未交餐的份额及餐券立即不可使用；餐券返回 CANCELLED。
- 退款按原资助批次执行 `refundBatch`，只退尚未交餐的原金额，地址固定为原付款人。商家或原付款人均可触发，不可改收款地址。
- 停业和资产转账分开。停业后显示“待退款”，实际退款收据确认后才记为已退款；不能把停业本身显示成款已退回。
- 原付款人已自行退款时，商家的原请求只确认“已退回”，不会第二次付款。
- 仅解除最后一张被本次停业取消的券对应的领取间隔；同一钱包后来在另一店领取的券及间隔保留。
- 已经交餐的餐券保留原 180 秒结算权利，停业不能吞掉商家已履约款项。
- 长期无人使用的自动退款期限仍未定，不实现擅自选择的半年或一年政策。

## 核心安全与恢复

- 数量、版本、价格、原用餐时段及全平台钱包间隔由合约和后台共同核验；不靠按钮隐藏限制。
- 平台 Claim 使用签名后持久化再发送的 outbox；结果未知只查询。已关闭店铺的未签名领取任务可根据最终链上证据安全终止，不阻塞其他领取。
- 钱包拒签或无哈希未知请求可由用户明确作废：只发送同原 nonce、零金额、空 calldata、到本人地址的交易。只有最终规范链收据证明原 nonce 已失效、原业务未完成，才取消占用；不能凭 4001 或本地超时取消。交餐须等旧 permit 过期，仍有效的券保留原实际交餐责任并建立新的确认步骤，不重复交餐。旧异步查询不得复活已取消状态。
- 所有商家/支持者写交易绑定账户、nonce、链、目标、value、calldata 和原请求。到账必须有规范链最终收据、确切事件和状态，不以浏览器成功提示代替证据。
- 资金核算按店铺隔离。陌生店铺的外部资助不能令应用内所有厨房不可用；公共账核验全合约守恒，应用内批次按对应店铺核验。
- 已登记店铺的外部链上资助由逐页只读索引发现：每页最多 10 块，固定目标和店铺、已确认登记块、最终块及规范区块哈希。未同步完的店铺单独显示进度，不能假装库存或退款完整。
- 外部发布的新版本缺少产品元数据时暂停该版本新资助；不编造菜单内容，原已资助且有完整承诺的餐食仍按原规则领取。
- 公网入口不能提供本地钱包桥、私钥导出或本地链配置；桥仅在精确本机配置下挂载。
- 新 schema 与旧 MVP 独立。数据库运行角色最小权限，RLS 与权限门禁显式检查；不把管理员数据库连接用于应用运行。
- ethers 从 6.15.0 升至固定 6.17.0，补入后端锁文件。运行依赖审计已为 0；开发依赖审计仍有测试工具的 moderate 告警，不宣称所有依赖均无问题。

## 实测证据与局限

最新本地回归：合约 71/71；后台 183 通过、3 个显式依赖用例默认跳过；前端 151 通过、1 个真实 provider 用例默认跳过。真实 PG+Anvil+HTTP 另跑 5/5；真实 nonce 作废另跑 9/9。具体证据范围如下，重复执行的测试不累计冒充不同用例。

- 真实 PostgreSQL + Anvil + HTTP/SIWE：完成登记/发布/资助/平台 Claim/验券/交餐/停业/退款/另一店立即再领/已交餐券结算，以及余额与债务守恒。自动测试只推进其独立本地链的时间。
- 浏览器主流程：商家发布、支持者资助 12 份、领取者 Claim、原钱包链接访问控制、检查/锁定/实际交餐、实际等待 180 秒再结算；390px 与 1440px 无横向溢出或页面异常。
- 浏览器停业流程：两笔资助共 5 份，领取后停业，餐券作废、间隔解除、原付款人收到两笔准确退款；另一个厨房立即领取成功。
- 浏览器拒签作废：支持者拒签后显式零转账作废，再资助仅扣一次餐款；商家确认实际交餐后拒签，作废并真实等原 permit 过期，保留原责任继续钱包确认。1440/390 餐品卡两个按钮均不重叠并可真实点击。
- 浏览器断网恢复：真实交易已发送后丢弃 RPC 返回，刷新仍保留 SEND_UNKNOWN；补原哈希后确认原付款，未增加发送或扣款。
- 浏览器使用本地合成测试钱包，不使用用户真实钱包，不等同公网验收。两处实测发现的界面问题（切钱包后保存链接与旧领取目标冲突、并行请求丢失券列表）已修复。
- 新独立 GitHub workflow 已在代码提交 `c69a20162d54a600fe13f2e5bb13898ebbc9334e` 全部通过：[CI 41098323191](https://github.com/3956ray/MealForward/actions/runs/41098323191)。验证合约、后台、前端、真实链适配器、真实nonce作废和真实wallet provider，并为旧认证提供真实 CI PostgreSQL。前两次CI分别暴露offline编译器和缺测试资产构建文件，均修复后重跑。

本地浏览器证据分别保存在 `/tmp/mealforward-real-browser-acceptance-resumed/`、`/tmp/mealforward-real-browser-closure/`、`/tmp/mealforward-real-browser-recovery/`、`/tmp/mealforward-real-browser-cancellation/`。它们是本机运行证据，目录可能随系统清理，不应作为长期公开链接。

## 当前用户验收入口

[打开新版](http://127.0.0.1:56527/product-v2/index.html)，仅此电脑可访问，需保持本机进程运行。右下角选择“领取者”→连接本地测试钱包→领取→保存餐券；切商家后可验券、交餐并等180秒结算。支持者可新增资助；停业/退款建议最后测试，因为永久停业不可撤销。资产均为本次 TEST。

## 本机复现

参阅 [运行说明](../../t1-intents/product-v2/acceptance.README.md)。`seed` 会准备一家厨房、三道已发布餐品、7 份已资助餐食并保持运行；领取账户尚未使用，方便直接验收。每次启动使用新的隔离目录，测试私钥只存于进程内；停机后不能把旧目录当成可恢复的钱包环境。

## 公网验收剩余前置项

1. 已完成独立源码审查及上述 CI；公网部署时须固定该候选代码和重新核验部署产物。
2. 部署新测试网合约，建立专用平台权限、Gas 余额及严格 manifest；不能把旧合约地址当新合约或自动迁移旧记录。
3. 创建新专用数据库角色/数据空间，配置新独立服务的 TLS 连接和秘密；不在交接、Git、工具输出或日志中写密钥/签名/连接串。
4. 验证公网 HTTPS、最终区块读取、平台 Claim、后台持续处理和恢复后，再由用户以自己的测试钱包做人工验收。

只有完成这些步骤，才可提供“新的公网实链验收网站”。本地入口及准备好的公网启动代码都不能替代这个结论。
