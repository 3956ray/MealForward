> 后续实施更新：核心链路的独立候选版本已开发，详见[实际实现与交接](2026-10-30-product-foundation-implementation.md)。下面的原版本证据及文档阶段范围保留；最新Gas与餐券入口选择以本次用户确认更新。

日期：2026-10-30（Asia/Shanghai）。交付类型：产品流程与接入评估文档，不是功能发布或合约实施规格。

## 1. 结论、依据与版本边界

原 Site 已有完整的主要产品链路，包括页面、弹窗、角色权限、状态变化、历史和异常恢复。后续开发应继承这些设计，再接通真实服务并应用最新用户规则；不能把单份串行钱包验收等同于完整产品交付。

### 1.2 事实与规则的优先关系

- 当前实现：对应源码、测试和部署证据判定；不得把设计目标写成已上线。

- 云端部署、数据库两笔 SETTLED 和钱包补测状态沿用 [HANDOFF](../../HANDOFF.md) 的既有记录；本轮未重新查询 Render、Supabase 或链上状态。

## 2. 页面、弹窗与角色链路

“页面”是可导航的地址；“弹窗”承载原页面内的编辑、审核及进度；“钱包”是用户明确操作后打开的扩展确认。关闭弹窗不能取消已经提交的请求或交易。

### 2.1 路由地图

| 用途 | 原 Site v8 | 后续完整真实模式 | 接入原则 |
|---|---|---|---|
| 首页、列表、说明 | `#home`、`#stores`、`#how` | 同名入口，其中列表/说明可定位首页区块 | 保留公开浏览及资助、领取入口 |
| 厨房详情 | `#store/{storeId}` | 同名结构、真实店铺标识 | 菜单、价格、版本、时段与数量来自已发布记录 |
| 厨房注册 | 固定邀请店主，无注册链路 | `#register` | 显式注册或继续原登记，不因无店铺而自动创建 |
| 商家工作台 | `#merchant/overview`、`meals`、`verify`、`payouts` | 同名结构 | 验证所属厨房；工作台切页不要求重复登录 |
| 我的支持 | `#mine/orders` | `#contributions` | 原订单及原请求可恢复，不能跳入模拟历史 |
| 我的餐券 | `#mine/coupons`、`#coupon/{id}` | `#mine`，券在相应流程展示 | 必须连接真实身份与原券；旧路径需要明确兼容或提示 |
| 商家验券深链 | 模拟文本凭证 | `#verify?code=…` | 读取短时凭证后移出地址栏，打开链接不核销 |
| 公共账、NFT、说明 | `#ledger`、`#nft`、`#about` | 公共账有读取接口；旧 coupon/NFT 有未接通提示 | 没有真实能力时不显示模拟成功 |

当前单份测试版使用 `#businessId=…&role=…` 和独立 recipient 页面，不具备以上完整路由语义。不能只改地址字符串就宣称接通。

### 2.2 访客、登录与身份切换

1. 访客可浏览厨房、餐品、价格、时段及公开汇总。
2. 资助或领取时需要钱包登录；商家身份由后台店铺权限判定。支持者与领取者是业务角色，同一账户可分别操作，不自动将捐赠变为给自己买餐。
3. 原演示选择固定 `.invalid` 邮箱并模拟钱包；后续完整前端登录后按厨房权限跳工作台或列表；当前测试版仅接受固定 Owner/Donor/Issuer。
4. 目标应保留登录前选择的厨房、餐品和数量，登录后重新审核有效条件。后续完整前端目前主要按身份跳转，这一返回目标机制尚需补齐。
5. 切账户、会话失效或退出时清除旧身份私有界面、临时授权和显示码，保留服务器原请求及历史。登出返回公开入口；后续旧实现统一回 `#register` 的行为应调整。

成功标准：后端身份验证成功且权限匹配，不能将钱包已连接等同于业务登录成功。晚到的旧账户响应不得重新填充页面。

### 2.3 商家入驻与餐品管理

入驻：主动进入注册页 → 填写厨房及首餐 → 保存登记 → 审核并签署授权 → 明确启用部署 → 查询原部署/首餐发布 → 具备管理权限后进入概览。

- 保存失败保留输入；刷新后继续原登记，不创建重复厨房。
- 合约确认和首餐公开是两个结果，不在保存表单后显示“已营业”。
- 入驻业务审核政策尚未定案；已有注册技术流程不等于已有商家审核制度。

餐品：管理页 → 空白新增或所选餐品编辑弹窗 → 保存草稿 → 发布审核 → 原发布进度 → 已发布菜单。

- 名称、图片、内容、单价和用餐时段属于版本条款；草稿不影响公开菜单，已支付订单与餐券固定原版本。
- 原演示时段支持 UTC+8 一至两段、分钟精度及结束时间 24:00；后续真实模式限制整点/半点。时间精度是已发现的实现差异，最终产品控件规格仍需统一，不能在本轮文档中擅自选择并改写历史时间。
- 新目标增加可资助数量、补量和资助截止时间。必须区分“尚可被资助的库存”和“已获资助、可被领取的份数”。上架本身不产生捐款或可领取餐食。
- 商家发布时完成必要授权，后续每次资助不要求商家逐笔签报价；具体授权实现需进入新合约规格。
- 下架停止新资助，保留已资助份数的领取及后续履约。价格或内容变化发布新版本。
- 工作台新增“今日休息”，店铺公开显示状态，保留正常用餐时段。不得直接调用旧安全暂停来实现；按钮恢复方式仍需细化。食材不足由商家自行公告和线下处理，不增加预测或实时库存保障流程。

### 2.4 Donor 资助与历史

厨房列表/详情 → 支持弹窗选同一餐品的份数 → 审核价格、版本、总额、付款钱包 → 明确确认原请求 → 钱包授权（需要时）及付款 → 查询原交易 → 支持成功。

- 改换餐品需明确保留或替换当前选择；改数量、付款账户、价格或版本后重新审核。
- “一键业务付款”可以协调必要的钱包步骤，但用户仍明确确认钱包操作；授权不等于付款，交易提交不等于最终确认。
- 成功后提供“查看我的支持”“继续浏览”或关闭返回原厨房，不自动进入领券。
- 历史保留时间、厨房、餐品、份数、金额、交易和汇总履约进度；不向支持者披露领取身份、链接或凭证。
- 关闭、刷新或断网后从原支持记录恢复。已知 hash 回写失败只补录原 hash；UNKNOWN 只查原请求，不重新支付。
- 报价过期须先核对原付款是否可能已发出；不能无条件生成替代订单。

成功标准：后台核验对应付款交易、金额、资产、原请求及资金入池后显示成功；可领取份数与已确认资助保持一致。

### 2.5 Claim、我的餐券与取餐凭证

钱包登录 → 选择已获资助餐品 → 显式 Claim → 后台确认唯一份额及领取资格 → 领取成功 → 显示餐券/保存入口 → 我的餐券恢复 → 到店时生成短时凭证。

- 任何钱包可领取，不需要 Issuer 人工逐笔发券；钱包不等于自然人，不宣称已实现真人去重。
- 每钱包全平台领取间隔与券有效期：内测均 2 小时；正式均 72 小时，均从领取成功计时。不叠加每日一次，提前使用不缩短领取间隔。
- 领取失败不扣资格；双击、跨标签、跨店并发必须只成功一次。未决领取保持原请求及资源，不能因前端超时重新领取。
- 非营业时间、临时休息时仍可领取并展示时间；已下架但存在资助的份数也可领取。取餐仅在券的原用餐时段内。
- 未使用券到期失效、份额回原资助池；旧券/旧码不复活，不增加捐赠次数，也不延长原券。
- 原 Site 券链接依赖当前浏览器模拟数据；后续 `#verify?code=…` 是短时商家凭证；当前 MVP 的 invite/exchange 是另一种长期凭证机制。三者不能混用。
- 新产品要同时明确“可保存、跨设备找回餐券的入口”和“到店短时验券码”。用户现已确认：长期入口必须由领取时的钱包登录才能打开，不是仅持链接即可使用的转让凭证。

原演示短码有效期不超过 120 秒、券到期和原用餐时段结束；生成新码撤销旧码。生产接口应验证这些条件，不能只隐藏按钮。

### 2.6 商家验券、交餐与结算

验券页或概览工具 → 扫码/粘贴码 → 检查所属厨房、券有效性与时段 → 取得唯一处理权 → 实际交餐 → 明确确认交餐 → 已使用/待结算 → 收款页面 → 等待 180 秒 → 审核结算 → 商家钱包发送 → 核验到账。

- 检查不消费餐券；打开验券链接不能自动锁券、交餐或付款。
- 错店、过期、已用及不在用餐时段的凭证被拒绝；扫码不可用时保留粘贴/输入入口。
- 原演示和后续完整模式分开锁券与交餐；当前 MVP `redeem` 合并链上锁定/交餐报告。下一阶段应明确产品动作与链上原子操作的对应，不能机械地多发或少发一笔交易。
- 已锁定、已交餐或 UNKNOWN 责任不能按普通未使用券自动释放；需要查询原操作。
- 180 秒以链上允许结算时间为准；倒计时只是提示，不自动放款。
- 原 Site 的结算是模拟状态转换，没有真实链上180秒等待；其验券使用模拟文本凭证，不证明摄像头扫码或数字码已接通。当前钱包版已有短时二维码/数字码及180秒合约门槛，需将这些已验证模块接回完整产品流程。
- 确认结算后，需核验原交易、券状态、金额及商家收款证据。已交餐和已收款必须分开显示。
- 商家交餐声明不构成独立证明某个自然人实际用餐。

### 2.7 公共账、退款与异常

公共账展示已验证汇总和履约活动；没有数据、真实零值、读取失败不能都显示为零。NFT 仅为原型感谢卡/可选意图，未接真实铸造时不得显示铸造成功。

原演示允许原付款人退回空闲且未预留份额，未设置半年/一年等待条件；该行为不是最新退款政策。用户已确认永久停业应退还剩余未履约资助；长期未使用拟到期退回，期限、触发方式及有效券/待结算款处理仍待定。

共同恢复约束：页面返回不重放写操作；关闭弹窗不删除原请求；拒签不冒称完成；身份变化丢弃旧响应；网络恢复只查原记录；UNKNOWN 不自动成功、不生成新付款、不自动解除资源占用。

## 3. 份额、餐券与操作状态

以下是原 Site 的模型语义，生产状态名称可不同，但不能丢失区分：

| 状态 | 含义 | 合法推进 |
|---|---|---|
| A | 已获资助、待领取 | 唯一领取确认后进入 R；符合退款政策的空闲份额进入 X |
| R | 已领取的份额 | 交餐确认进入 H；未锁定、无未决责任的券过期返 A |
| H | 已交餐、尚未结算 | 合法结算确认后进入 S |
| S | 已结算 | 保留历史，不再次支付 |
| X | 已退款 | 保留原退款归属，不再提供领取 |

总资助份数 `F = A + R + H + S + X`。价格按每份原订单计，金额也须按原价守恒，不能以新菜单价格重算历史。原模型可领取数为 A 中未被未决操作预留的部分。

券自身另有 `issued → locked → reported`、`expired` 状态；锁券时份额仍为 R。操作自身另有 `pending / unknown / rejected / final`。三层状态不能合成一个“完成”字段。

新库存还需表达可接受新资助的发布数量及付款中的预留；它不属于已经入池的 F。过期返池是 R→A，不是新增资助，也不自动增加可接受资助的商品库存。

原 Site 的源级核对索引（均在 v8 的 `dist/model.mjs`，页面绑定在 `dist/app.js`）：

| 流程 | 模型函数 | 版本证据与目标差异 |
|---|---|---|
| 登录与商家权限 | `signIn`、`merchantStore`、`authorize`、`signOut` | 固定邀请邮箱；生产身份与权限由真实后台承担 |
| 餐品新增/草稿/发布 | `createMeal`、`saveDraft`、`publish`、`setListing` | 已隔离草稿和版本；未实现新库存补量及资助期限 |
| 资助与结果确认 | `support`、`resolve` | 原请求冻结版本与数量；模拟签名/支付，店铺累计10份限制需废除 |
| Claim与资格 | `claimPreview`、`claim` | 原份额优先顺序和原条款已实现；演示按邮箱72小时且下架/暂停会阻断领取，新规则不同 |
| 取餐与恢复 | `recover`、`credential`、`checkToken` | 有身份校验、旧码撤销、原时段和短期到期；不是长期跨设备链接 |
| 唯一锁、交餐与结算 | `lock`、`report`、`settle`、`resolve` | 阶段分离，模型模拟最终结果；需接真实交易与180秒等待 |
| 过期与退款 | `expire`、`refund`、`reserved` | 未决资源不释放；原演示退款条件不是最新退款政策 |
| 历史/账目与异常恢复 | `stats`、`validate`、`restore`、`transaction` | 保留原责任、金额守恒和损坏数据；本地存储可编辑，不构成生产账本保障 |

原模型没有商家注册/部署接口，不能为入驻流程伪造原Site调用证据；入驻证据来自后续完整前端的 `saveRegistration`、`signRegistration`、`enableRegistration`、`getRegistration`。

## 4. 页面动作到接口和链上证据的映射

下表接口是仓库已有后续完整模式的调用/路由，不是宣称当前 Render MVP 已提供它们。前端依据 [live-api.mjs](../../sites-frontend/dist/live-api.mjs)；后端路由依据 [application.py](../../cp30-backend/src/c1/application.py) 与 [live_gateway.py](../../cp30-backend/src/c1/live_gateway.py)。同格中未写全 `/v1` 的路径是相应资源的子路径，正式接口规格必须展开；启动连接检查使用 `GET /v1/connection`、`GET /v1/identity/setup`，只读取能力，不触发业务。

|---|---|---|---|

## 5. 接入差距与建议顺序

### 5.1 已确认的合约/后台障碍

[MvpStoreEscrow.sol](../../mvp-contracts/contracts/MvpStoreEscrow.sol) 明确固定 `LIFETIME_CAP=10`、`VOUCHER_LIFETIME=259200`，采用小范围份额编号/位掩码；`fund` 校验绑定付款人的报价签名；`issue` 要求 issuerAuthority 且 `_open` 同时检查下架/暂停/关闭。`refund` 当前仅允许原付款人操作 A 份额，不含新退款期限政策。

[service.mjs](../../t1-intents/mvp/service.mjs) 要求已有业务全部 SETTLED 后才能创建下一笔；[chain.mjs](../../t1-intents/mvp/chain.mjs) 固定角色、商家、餐品、金额和全天时段。当前链上券不绑定领取钱包，因此不能据当前合约声称已实现跨店钱包冷却。

结论：持续补量、2小时券、自主领取和下架后领取需要新合约版本与后台规格，不能只改前端常量。扩大10份上限也不能只修改一个数值；必须重新检查编号类型、遍历成本、退款表达、并发及账目验证。新设计不升级、覆盖或迁移既有已部署记录。

### 5.2 推荐复用边界

- 产品结构与视觉：继承原 Site，保留角色导航和弹窗；用现有 React 产品承载方式逐步接入，参考后续完整前端的行为与接口，不直接加载其全部历史运行配置。
- 钱包：沿用当前 Wagmi/Viem 连接、会话失效与原交易恢复模块；后台查询不会触发连接、签名或发送。
- 后台：建立多店、多餐品、多笔原请求的数据模型；全平台钱包资格和份额分配须原子校验，商品版本与订单条款不可变。历史查询按身份授权。
- 合约：在新规格中明确一次上架授权、捐赠并发、发券权限、有效期、下架与休息的独立语义、退款和扩容；继续复用已验证的资金/重放保护组件。
- 凭证：把可保存入口、券所有权/恢复和短时展示码拆开；使用后者验券，避免将长期秘密暴露给商家、Donor、公共账或日志。
- 兼容：保留旧入口、原记录和原 hash 恢复路径。新功能独立开关、先隔离测试；不以回退为由删除数据或重发交易。
