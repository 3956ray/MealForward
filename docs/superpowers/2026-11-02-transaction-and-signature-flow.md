# MealForward 当前交易与签名流程（2026-11-02）

口径：当前公网源码75e207f，新版共享Escrow 0x999Edd25dBB7716D63a5360350dbD892b82312bD；正常成功流程，新厨房、新餐品、一个资助批次中的一份餐完整履约。初始无足额allowance。不计合约部署、测试币充值、退款、撤销/补量和失败交易。登录消息签名、链上交易及用户确认必须分开统计。

|步骤|用户操作/后台行为|链上交易|交易发送者/Gas承担者|USDC位置|
|---|---|---:|---|---|
|登录|各角色用钱包签登录消息；有效会话可复用|0|无需Gas|不变|

首次全程7笔：商家4、donor2、平台1。已有厨房、发布新餐品6笔；已有厨房与已发布餐品5笔。足额allowance可省去授权交易，分别再减1。发布时一次可配置多份，登记/发布不逐餐重复。单次资助N份共享approve+fund；若N份均正常领取、交餐、结算，则已上架条件下为2+3N笔（没有额外补量/失败/退款等）。实际已验证批次资助3份，仅1份履约，不能说3份全结算。

人工钱包签名口径：7笔链上交易中6笔由人确认，平台claim自动签名。若三个角色各用独立钱包、各首次登录一次，再加3次登录消息签名，共9次人工签名动作；不含连接/切链/解锁等非签名弹窗，亦不是固定每餐9次。后台另签验券许可，不弹用户钱包，也不另增链上交易。领取人登录后领取/展示券不需要额外交易签名。

当前结算：链上redeem成功才进入HANDED_OVER；180秒后审金额/收款人→准备结算请求→商家钱包确认→后台核验原交易→SETTLED。USDC在settle内直接转给商家，无额外提现/商家approve交易。_active要求商家owner，settle把钱转msg.sender，当前不能让平台直接代发。等待、审核、查询不是链上交易。结果未知只查询原操作。

一次签名的边界：授权与付款可在支持的账户/网络上用EIP-5792原子批处理，实际能力需查询；账户启用可能有额外确认。当前尚未实现，后端的额度前置、单笔外层交易证据与恢复需适配。Permit是签名授权机制，不自动保证一次用户签名覆盖付款。各角色不同时间做决定，不能把整个履约链当作一笔原子交易；现有180秒约束明确阻止交餐与结算同笔完成。

建议体验目标（未开发/未部署）：登录会话有效时，donor一次付款确认；领取人确认领取不弹交易钱包；商家交餐确认一次、到时自动结算。最后一项需新合约授权设计：代发者不能改变固定商家收款地址、不得提前/重复结算；平台承担结算Gas/可靠调度需作为新规则落实。保留180秒时，优化后的既有餐品成功流程仍为4笔：合并资助、领取、交餐、结算；自动化减少人的确认数，不消除后面的链上交易。不得迁移已部署合约或历史资金来实现本次说明。
