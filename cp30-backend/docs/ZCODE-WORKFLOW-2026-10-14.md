# CP30 ZCode 开发流程（2026-10-14 接手后）

本文档定义接手后在本仓库工作时的标准流程。配套资源：

- 常驻上下文：仓库根 `AGENTS.md`（顶部「CP30 接手运维层」+ 各 CP 冻结合同）
- 排障手册 skill：`.zcode/skills/cp30-ops/SKILL.md`
- 健康检查命令：`/cp30-status`
- 交接真源：`docs/WEB-GPT-HANDOFF-2026-10-14.md`

## 为什么是这套流程

本项目有三个特殊性，决定了流程形态：

1. **接手项目**：原作者不在，状态真源分散在交接文档、运行时目录和会话记忆里。最大风险不是写不出代码，而是**状态漂移**（以为的进度和实际不一致）。→ 所以每个会话必须以状态对齐开场、以交接更新收尾。
2. **独占写者架构**：签名 journal 独占、六服务直接从源码树加载代码、单一主开发写者是冻结合同要求。→ 所以**不用并行子代理写代码**，写操作必须串行；子代理只用于只读探索（查日志、读代码、搜历史）。
3. **带实库的 live 系统**：`~/.mf-cp30-20261013/` 是真实运行时（链上已发布 intent、热修复过的生产库）。→ 所以验证靠只读探针 + 浏览器实测，而不是随手跑测试重建环境；误操作的代价是实库不可重建。

## 标准会话流程（五步）

### 1. 开场：状态对齐
- 跑 `/cp30-status`，得到服务/前端/intent/attempts/日志的快照
- 对照交接文档「当前进度」节，确认今天要推进的卡点还在不在（上一个会话可能已经解决或产生了新残留）
- 若快照与交接文档矛盾，**以实库和日志为准**，先更新认知再动手

### 2. 动手前：计划审批（非平凡改动必走）
涉及以下任一项，先出计划、用户确认后再执行：
- `send_original` / admission / ledger 回滚逻辑（当前卡点正 here）
- 任何 `connection-migrations/` 文件（必须走「改文件 → 重 pin → fresh-PG 验证」三步，**禁止只热修生产库**——043 的教训）
- 服务启停、任何触碰实库的 SQL
- 探针脚本超过 20 行

小改动（读代码、写只读探针、改文档）直接做。

### 3. 执行：单写者串行
- 一次只推进一个卡点；改 `src/` 前先停服务（六服务从源码树加载）
- 需要大范围搜索/读日志时可以派**只读**子代理并行，但写操作永远单线程
- 遵守 `cp30-ops` skill 的红线清单（UNKNOWN 不重发、实库不清不重建、UTC+8、不输出密钥内容）

### 4. 验证：三层闭环
每完成一个修复或一步推进，依次验证：
1. **探针层**：只读 Python 探针 / psql 查 `c1_live_private.intents` 的 action/stage/transaction_hash，确认状态机走到预期阶段
2. **日志层**：`automatic-business-*.log` 无新增真实异常（背景噪声 `BUSINESS_CODEC_UNAVAILABLE` / `LIVE_STEP_FAILED` 除外）
3. **端到端层**：前端 `https://localhost:16443` 浏览器实测（注意精确 Host、review 窗口 300 秒内确认），钱包签名步骤交给用户执行

任一层失败，回到第 2 步重新计划，不带病推进。

### 5. 收尾：交接闭环
- 更新交接文档（`WEB-GPT-HANDOFF-*.md` 或新建当日节）：写清「本会话改了什么、验证到什么程度、下一个卡点是什么、涉及的 opId/ID」
- 提醒 agent 更新跨会话记忆
- 有代码改动则 git commit（只提交源码树，运行时目录与密钥不入库）

## 三轨并行模型（2026-10-14 补充）

「单写者串行」约束的是**同一文件的写操作**；跨轨文件互不重叠时可以并行。项目冻结合同本来就允许「最多三个开发助手、文件不重叠」——三轨正好对齐：

| 轨道 | 拥有 | Skill | 状态 |
|---|---|---|---|
| 前端 | 根 `src/`、`index.html`、`vite.config.ts` | `cp30-frontend` | 常规开发 |
| 后端 | `cp30-backend/**` | `cp30-backend`（排障用 `cp30-ops`） | 常规开发，迁移走三步铁律 |
| 合约 | `cp30-contracts/**` | `cp30-contracts` | **冻结只读优先**，改动先立新阶段授权 |

### 接口冻结层（并行能成立的前提）

三轨之间的契约只有三样，都有可校验的真源：

1. **ABI**（合约→全轨）：`cp30-contracts/out/` 产物，副本 `shared/MealForward.abi.json` 与 `indexer/abis/` 必须一致
2. **链上登记册**（合约/部署→全轨）：`~/.mf-cp30-20261013/chain-profile-public.json`，`chainProfileDigest` 是指纹——digest 变 = 接口变
3. **HTTP API 语义**（后端→前端）：错误码、状态机阶段、字段名；变更走交接文档「接口变更通告」

规则：任何一轨动了接口，先通告、全轨确认同步后才算数；联调（`/cp30-integrate`）Phase 1 会机械校验前两条。

### 并行的三种执行方式

1. **多窗口（推荐日常用）**：三个 ZCode 窗口打开同一仓库根，各自声明轨道；skill 按任务自动触发，边界靠 skill 里的文件清单
2. **同会话后台子代理**：一个会话里派后台 agent 并行做三条轨的任务，每个子代理 prompt 里注明轨道 skill 路径 + 文件边界；适合中型批量任务
3. **动态 workflow**：结构化 fan-out + 门控（如「三轨各自实现 → 接口校验门 → 联调」）适合重复性的大批量任务，需要时让 agent 用 CreateWorkflow 现建

### 并行期纪律

- 运行时（`~/.mf-cp30-20261013/`）是共享资源：**同一时刻只允许一个轨操作服务启停/实库**；后端轨默认持有此权，其他轨要动先协调
- 各轨收尾各自 git commit（按轨归因），不混提交
- 联调不是随时做：三轨都到可验证状态后，走 `/cp30-integrate` 四阶段（就绪检查 → 接口同步 → 重启 → E2E → 归档）；联调中发现的问题**记录并标注责任轨**，回各轨修，不在联调现场跨轨顺手改
