# MealForward · Three Stores

CP29-UI08 public card hover and status badge repair on accepted UI07 for the selected English Three Stores Site. Static HTML, CSS and JavaScript modules; no installation or build. Public hero, three kitchen cards, bowl mark and approved local photographs remain. Merchant headings use system sans-serif, light meal rows and one prominent verification tool.

Run locally: `python3 -m http.server 4173 --bind 127.0.0.1 --directory dist`.

Verify: `node verify.mjs`; syntax: `node --check dist/app.js`, `node --check dist/model.mjs`, `node --check browser-verify.mjs`, `node --check card-verify.mjs`. The isolated workstation browser harness requires installed Chrome, bundled Playwright and an owned loopback server on 15645. It creates fresh temporary contexts, allows only loopback/data requests, and writes current evidence to the UI08 Developer `evidence` directory. Its absolute runtime/evidence paths are QA-only, not Site dependencies.

Routes: `#home`, `#stores`, `#how`, `#store/{qinghe,shiguang,nuanxiang}`, `#ledger`, `#nft`, `#about`; private `#mine/coupons`, `#mine/orders`, `#coupon/<id>`, `#merchant/{overview,meals,verify,payouts}`. Original `#merchant` and `#mine` shortcuts still work.

Sign in selects fixed synthetic `.invalid` accounts. Visitor/neighbor can support and receive; each owner has a fixed invitation to only its kitchen. All operations are local simulations: no real email/OTP, wallet extension/provider, chain, NFT minting, camera, API or database. LocalStorage is user-editable; this demonstrates application consistency, not production authentication or financial security.

Overview and Verify share the same check/lock/report component and handlers. Checking is non-consuming. Unique lock, explicit handover/report and individual owner payout remain separate. Navigation retains original cases and unresolved operations. Sign-out/direct Sign in/restoration revoke current authority, wallet, displayed codes and transient approval without deleting history, locks, pending operations or cooldowns.

Meals has an independent `+ Add meal` blank form. Valid save creates a stable store-bound meal ID and draft; it creates no stock and is not publicly supportable/claimable. Confirmed first publication lists the meal. Editing/publishing later changes only that meal's future version and preserves its listing. Service Time uses one or two independent clickable start/end selectors in Asia/Shanghai, at full-minute precision including 24:00 as a legal end. An adjacent plus adds a second row; Remove cannot leave zero rows. Blank, reversed or overlapping rows remain visible and cannot be saved. Existing orders/vouchers retain original terms. Unlisting preserves the object and all obligations; store safety pause is separate. There is no manual inventory input or destructive meal deletion.

Each order contains one kitchen/meal and multiple portions of that same meal. Changing selection requires Keep current selection / Replace selection. Approval binds email, payer, store, meal ID, quantity, price, version and NFT choice, and is checked again at payment. A queued payment consumes transient approval. Direct account changes preserve cart intent but require a new connection/approval/confirmation.

Schema 3 separates store safety settings, independent meals/version history and original record associations. Support intents freeze original terms. Claims select only free/unreserved units of the chosen meal in original sequence and show those actual original version/price/windows before confirmation. The store lifetime cap of ten includes all meals, versions and open support reservations. Original-unit prices drive all counts/money; refunds/consumption never reopen the cap. Global email cooldown and original voucher expiry remain 72 hours; display code is at most 120 seconds and ends no later than the original expiry/service-window end. UNKNOWN retains the original operation/resources and never auto-resolves.

Schema-1 migration accepts the actual baseline field structure. Schema-2 migration accepts the known single-menu shape and preserves all original operations/resources, including UNKNOWN. Both map each store's original single menu and all its historical versions to `legacy-<store>`, without changing original IDs, prices, raw content, status, expiry or payer. Schema 1 lacks captured content/image/windows: only its actual baseline fixed store definitions supply those missing fields. Unknown/mixed schemas, conflicting original versions or unresolved references block and preserve original bytes; no silent reset or restored login. Legacy ownership that cannot be proved remains unassigned.

Model/static tests cover original safety and P1/P2 regressions plus independent drafts, A/B inventory, shared cap, original versions, unlisting, explicit schema migrations and same-price meal approval binding. Browser tests cover complete original/multi-meal flows, desktop/tablet/mobile first screens, forms/keyboard/focus/errors, legacy/mixed data, images/English/overflow and observed requests. Native publication, production auth/security, real wallet/chain/Gas/NFT and multi-client concurrency are not verified. Leader owns fixed-source review, official packaging and publication; old saved v2 remains blocked.

Meal names and content, including HTML-like characters, are displayed as literal text in menus, reviews, vouchers and activity. A demo-only reset requires the currently open reset dialog's original confirmation button; arbitrary, stale or wrong-dialog actions preserve saved records and UNKNOWN responsibilities. Time errors remain next to their row, with a separate form summary.

Meal image offers an explicit Upload image action, unsaved preview and optional Bundled images. Only decoded PNG/JPEG/WebP input is accepted: at most4 MiB,4096px per side and8 megapixels. Header dimensions are checked before decoding; decoded dimensions are checked again. Browser canvas re-encodes an opaque JPEG (quality0.82), at most768px per side, reducing dimensions until at most192 KiB. Native JPEG APP/COM metadata is removed. Only the normalized result is saved on explicit Save/review; original bytes and filenames are never saved. Close, modal/editor replacement, bundled-image selection and account changes invalidate pending upload ownership. Failed upload or storage quota leaves saved bytes unchanged.

Model validation accepts only approved bundled images or bounded canonical JPEG strings with valid marker structure, dimensions, byte limits and no APP/COM metadata. Browser restoration additionally decodes every distinct persisted normalized bitmap before accepting state or saving cleared authority; malformed pixels block and preserve original bytes. Parsing alone is not claimed to decode JPEG pixels. Version/order/voucher image and Service Time terms remain immutable. No handwritten image encoder/compressor is used.

Public cards align corresponding row tracks within each grid row using CSS subgrid, with natural single-column heights. Published representative meal image/name/price/Service Time are from the same meal; draft times do not affect public output and representative hours are labelled Selected meal. Store supported/cap metrics and selected meal availability retain their distinct meanings. All public navigation anchors share font family, size, weight and line-height.

Fonts are local system sans-serif and Georgia. QRCode.js 1.0.0 is bundled locally under MIT; no runtime CDN. Approved illustrative assets remain:
