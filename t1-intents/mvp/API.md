# MVP API — integration contract

Factory `makeMvpHttp({pool, origin, pepper, enabled=false, writesEnabled=false, rpc?})` from `http.mjs` returns `{handle, close, service, store}`. Production RPC defaults to the existing globally paced bounded execution read-only adapter (45-second/80-call operation budget; six-second per RPC deadline; 1 MiB response cap). Pool must use dedicated mf_mvp_usdc_runtime; call `verifyRuntime(pool)` before enabling. Pepper is a NEW random private string >=32 bytes. No environment override of production chain/roles. Local tests use `makeLocalMvpHttp({... , policy, rpc})` and loopback origin only. `handle(req,res)` owns all `/v1/mvp` requests; static pages owned by coordinator.

JSON numbers representing uint256 are decimal strings; timestamps seconds. All POST JSON exact fields, pinned Host/Origin, same-origin fetch metadata. Authenticated POST uses `x-mvp-usdc-csrf`. Cookies: `__Host-mf_mvp_usdc_session`, `__Host-mf_mvp_usdc_pre`, `__Host-mf_mvp_usdc_recipient`, Secure/HttpOnly/Strict/Path=/. All responses no-store. Errors `{error:"UPPERCASE_CODE"}`.

- `GET /v1/mvp/status`: public `{enabled,writesEnabled,chainId,testOnly:true,roles,meal,amount:"7000000"}`.
- `POST /v1/mvp/auth/pre-session` `{}` with `x-mvp-usdc-bootstrap: 1` → `{csrf}` + pre cookie.
- `POST /v1/mvp/identity/wallet/challenge` `{address}` + pre csrf → SIWE challenge (`message`, `challengeId`, …).
- `POST /v1/mvp/identity/wallet/login` `{challengeId,signature}` + pre csrf → `{csrf,authPilot:true}` + wallet session. Only pinned Owner/Donor/Issuer accepted.
- `GET /v1/mvp/me` → `{wallet,role,csrf}`; same-origin check and rotates CSRF, allows reload recovery.
- `POST /v1/mvp/auth/logout` `{}` + session csrf.
- `GET /v1/mvp/setup`: authenticated `{role,state,operations}`. Also returns `nextAction`, `allowedAction`, `disabledReason`, `quote:{verified,deadline}|null`, `invitationCreated`, `invitationOpened`, `settleEnabled`, `chainTime`. `state` contains confirmed phase (`TOKEN_READY`, `READY`, `APPROVED`, `FUNDED`, `ISSUED`, `HANDED_OVER`, `SETTLED`), token/escrow once verified, voucher/expiry/settlementAvailableAt once issued. `operations` contains only current wallet operations. No signed quote or invite secrets.
- `POST /v1/mvp/quote` `{}` Owner explicitly creates one 30-minute draft; repeat returns same draft. Explicit POST replaces an expired draft only if no fund operation has ever been prepared. Returns `{typedData,verified}`.
- `GET /v1/mvp/quote`: authenticated existing draft, same response or null. No new draft on GET.
- `POST /v1/mvp/quote/verify` `{signature}` Owner verifies exact server draft → `{verified:true}`. Same verified signature cannot be changed.
- Prepare routes, each `{}` except redeem `{checkToken}`: `POST /v1/mvp/setup/escrow/prepare` (Owner); `/donor/approve/prepare`, `/donor/fund/prepare` (Donor); `/issuer/issue/prepare` (Issuer); `/merchant/redeem/prepare`, `/merchant/settle/prepare` (Owner).
- Prepare → operation DTO `{id,action,state,txHash,candidateHash,receipt,transaction?}`. `transaction` appears ONLY in PREPARED: EIP-1193 `{from,to?,data,value,nonce,chainId}` hex quantities. Repeated prepare returns stable same transaction; every action has one durable operation.
- `GET /v1/mvp/operations/:id`: own wallet only, same DTO, transaction retrievable only before attempt.
- `POST /v1/mvp/operations/:id/attempt` `{}` + CSRF: atomic PREPARED→SEND_UNKNOWN, exactly one caller gets `{allowed:true,operation}`. Frontend retains transaction obtained BEFORE attempt; only winner explicitly invokes wallet. Losers get 409. Attempt never returns transaction and is never reset even after rejection/response loss.
- `POST /v1/mvp/operations/:id/hash` `{txHash}`: durably saves candidate then validates original sender/nonce/input/value/target/chain, returns operation. Unindexed candidate remains visible as candidateHash; txHash only after verified. Unverified candidate may be corrected; verified bound hash cannot change.
- `POST /v1/mvp/operations/:id/reconcile` `{}`: retry safe. Uses finalized canonical receipt and historical accounting, never sends. Returns operation. States PREPARED/SEND_UNKNOWN/HASH_BOUND/CONFIRMED/REVERTED. Pending receipt stays pending; mismatch fails closed. Bind/reconcile remain available when writes disabled.
- `POST /v1/mvp/issuer/invite` `{}` only after confirmed ISSUED → `{token,expiresAt}` once. Construct `/mvp/recipient.html#<token>` and remove fragment immediately on recipient load. Repeat returns 409; no implicit rotation. Explicit `{rotate:true}` may replace a lost invitation ONLY before first exchange; setup exposes created/opened booleans. Opened invitations cannot rotate.
- `POST /v1/mvp/recipient/exchange` `{token}` + `x-mvp-usdc-bootstrap: 1` → `{csrf,expiresAt}` + recipient cookie. Invite 72h bounded by voucher expiry; recipient session <=8h. Recipient needs no wallet.
- `GET /v1/mvp/recipient/voucher`: same-origin recipient cookie → `{state,meal,amount,expiresAt,settlementAvailableAt,csrf}` (rotates CSRF for reload). No voucher identifier.
- `POST /v1/mvp/recipient/display` `{}` + recipient csrf → `{qrToken,code,expiresAt}`. QR encodes only qrToken. Display <=120s; refresh atomically invalidates old display/check handles. Blocked after redeem preparation.
- `POST /v1/mvp/merchant/check` `{code}` OR `{qrToken}` + Owner csrf → `{checkToken,expiresAt,meal,amount,state}`. Durable per-session 10/minute and global 30/minute guessing limits. Check handle bound to current display AND merchant session; redeem preparation consumes it atomically.

Do not send by effect/page-load or retry after /attempt. Status phase is confirmed business state; operation state is pending/recovery. Human declaration is not independent proof of physical food delivery. Countdown is advisory: settle preflight uses chain time and contract simulation. Kill writes blocks prepare/attempt/quote/invite/exchange/display/check, preserves login/status/bind/reconcile.

Existing USDC policy: production chain 10143 fixes token 0x534b2f3a21130d7a60830c2df862319e593943a3, decimals 6, code hash 0x96215e6049ed615cdc22fea7701e85458a8e51a2df3e7d45e8f9fa1d521b5a78. No token deployment route or token artifact runtime dependency. New mf_mvp_usdc schema starts TOKEN_READY and never updates old mf_mvp. New local recovery key mf-mvp-usdc-recovery-v2 ignores old operations.

/status includes currency {address,symbol:"USDC",decimals:6,existing:true}; /setup adds donorBalance (base-unit string), sufficientFunds, observedAt (seconds) inside currency. Currency observations are deduplicated/cached 30 seconds. Every prepare and attempt validates fixed address/code/decimals against finalized state; approve/fund additionally reject INSUFFICIENT_USDC. No fixed totalSupply assumption. Local-only loopback 31337 fixture predeploys ERC20 then injects its address/codeHash before business flow begins with escrow (six business transactions).

Background client reads are silent, serial with bounded 8–60 second failure backoff, skipped in hidden documents, and never touch input/error/busy state. Action epochs and wallet/session revisions reject stale responses; explicit actions remain serialized and are the only signing/sending path.
