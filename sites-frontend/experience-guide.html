一餐的旅程。
由你来实际检验。

这是留膳网站的交互验收入口。我们希望你先验证页面能不能让支持者、领取者与店主自然完成任务，而不是反复学习钱包、Intent 或 Journal 等技术术语。

重要：这是模拟环境，不是真实链上测试。

本页面中全部餐馆、账户、USDC、餐券、二维码、核销与结算都是浏览器本地演示数据。不需要 MetaMask，不会调用 CP30 实库，也不会产生真实交易或用户记录。不同浏览器及无痕窗口之间不共享数据。

测试前准备

使用一个普通浏览器标签页打开网站。页面底部有 Demo controls，可以将时间设为午餐时间、指定下一次原操作的结果为 Final/Pending/UNKNOWN，或明确重置演示数据。若测试二维码，请先点 Set demo lunch time。

支持者选择 visitor@mealforward.invalid 登录

青禾餐馆店主选择 qinghe.owner@mealforward.invalid 登录

逐条验收

01

支持者：选餐并完成一笔模拟资助

进入 Kitchens，点任一可资助餐品的 Support a meal，选择份数并核对单价与总额。按 Review support，使用演示账号登录，按引导连接 Demo wallet 并确认。打开原操作，点 Check original operation，再到 My meals → Support orders 检查订单。

数量与合计正确审批≠付款原订单可恢复

预期：订单只在被明确模拟为 Final 时显示成功，不能在 Pending 或 UNKNOWN 时伪造付款成功。

02

领取者：领取一餐并查看私密餐券

登录 neighbor@mealforward.invalid，选择有余额的餐品并按 Claim a meal，确认领取。进入原操作按 Check original operation，在 My meals → My vouchers 查找餐券并打开。测试 Show verification code，注意它是短时动态凭证。

领取限制餐券版本/到期二维码有效期

预期：在明确确认以前没有可用新券，超时凭证不会永久有效。此演示的领取身份是虚构邮箱；真实 CP31 钱包/无注册体验尚需独立验收。

03

店主：查看餐馆、编辑与发布餐品

切换到 qinghe.owner@mealforward.invalid，进入 Kitchen workspace → Meals。点 Add meal 新建草稿，设置名称、描述、价格、服务时段和图片；保存后发布，并确认公开菜单展示的版本与旧订单完全独立。

草稿不对外公开发布和上架历史版本冻结

预期：过去已经资助/领取的餐仍保留原价与原服务时段。这里是固定店主的菜单体验，不会真实部署合约或创建新餐馆。

04

店主：核销、确认交餐和结算

进入 Kitchen workspace → Verify & hand over。本地演示允许你先以该店主演示账号自行领取一张模拟券，再使用其 Use demo voucher code / 粘贴验证码演示 Check、Lock 和 Report；或直接到 Payouts 测试已有样例的店主结算。将下一次模拟结果设为 Final，然后检查餐账变化。

Check 不会消费Lock ≠ ReportReport ≠ Settle

预期：交餐确认与结算分离，资金状态只有原操作 Final 时才更新。注意：浏览器本地演示不能证明不同真实账户间共享餐券或链上收款。

05

异常恢复与隐私

使用页面底部 Demo controls → Next original-operation result 选择 Pending 或 UNKNOWN，重复支持/领取的查看操作；再尝试刷新、重新登录及进入公开 Meal ledger，检查是否把未知操作当作成功，以及是否泄露私人验证码。

UNKNOWN 不重发刷新不重置历史公开账本不泄露隐私

预期：不显示任何虚假的链上交易哈希、真实收款证明或领取者私人信息。
